# BUG-3163 — Racing write test hangs on Windows

**Item:** BUG-3163 — Racing write test hangs on Windows
**Branch:** `bugfix/bug-3163-racing-test-hang`
**Run:** vibe/2026-10-08-slow-hanging-tests

## Summary

`AtomicFileTests.AReaderRacingTheWriter_AlwaysReadsAWholeDocument` finishes, green, on Windows, and
can no longer hang. The bug it exposed is fixed in the product.

**The product bug.** On Windows, replacing a file that another handle holds open for reading is
refused with *access denied*. The callers of `AtomicFile` caught that refusal and logged it, so the
write was lost. They are `SettingsService`, `IdentityProfileStore`, `RepositoryListStore` and
`HiddenBranchStore`. Two instances side by side could lose a settings change or a recent-list update
whenever one read the file while the other wrote it.

**The hang.** The racing test's writer died on the first refusal and never released the reader. The
reader loop then spun forever at 100% CPU. Before the fix it ran for more than 3 minutes, and MTP's
`--timeout 45s` did not stop it. With the test fixed alone, it failed in 30 ms with
`System.UnauthorizedAccessException : Access to the path is denied.`

**How:**

- `AtomicFile` retries the final replace, on Windows only, while the target is held open.
  - Up to 50 attempts, 10 ms apart.
  - Retried refusals: access denied, sharing violation (`0x80070020`) and lock violation
    (`0x80070021`).
  - Any other error, and the last refusal, surface exactly as before, and the temporary file is still
    deleted.
  - The async write waits with `Task.Delay` under its cancellation token and checks the token before
    each attempt.
- The racing test's writer releases the reader in a `finally`, so a failing writer fails the test.
  The assertions are unchanged.

## Decisions taken at build time

| Question | Chosen | Why |
|---|---|---|
| Tests first | Yes. The two hold-then-release tests and the racing test were seen failing on the unfixed `AtomicFile` | Proves the tests catch the bug, and that the racing test now fails rather than hangs |
| Rounds in the racing test | Kept at 300 | Fewer rounds would weaken what it proves. It now takes about 4 s on Windows, because its reader re-opens the file in a tight loop and most writes wait out one ~15 ms sleep tick. A real reader holds the file for microseconds |
| How long a test reader holds the file | 50 ms | Far inside the retry budget (≥ 0.5 s) even at Windows' coarse sleep resolution, and long enough to force at least one refusal |
| The "never lets go" test off Windows | Skipped with `Assert.SkipUnless`, as `TokenStoreTests` does | Elsewhere the rename succeeds, so there is no refusal to assert |
