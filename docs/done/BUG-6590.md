# BUG-6590 — A refresh resets the working-tree diff

**Item:** BUG-6590 — A refresh resets the working-tree diff
**Branch:** `bugfix/bug-6590-diff-refresh-keeps-place`
**Run:** vibe/2026-10-06-diff-search-refs-release

## Summary

While the diff of an uncommitted file is open, the automatic refresh no longer moves the reader back to
the first change, clears their selected text, or undoes the context they widened.

**The cause.** At every refresh the working-tree panel re-reads the status and picks the same file
again, and the history used to hand that pick to `DiffViewerViewModel.ShowAsync`. That call:

- reset the context to its default;
- re-read the patch;
- replaced every row, which clears the selection;
- raised `PatchChanged`, which the view answers by scrolling to the first change.

It did all of this even when nothing in the file had changed.

**The fix.**

- `DiffViewerViewModel.IsShowing(repository, target, path)` says whether a file is the one on screen.
  The comparison is by value, because `DiffTarget` is a record.
- `DiffViewerViewModel.RefreshAsync(file)` re-reads that file with the options the reader chose
  (context, whitespace, size limit) and draws it only when it differs from what is shown. Two patches
  are the same when all of these match:
  - their patch text: the paths, the hunk headers and every line;
  - their change kind, modes, and binary, submodule and truncated flags;
  - the message shown in place of a patch.

  An identical read touches nothing: no rows, no selection, no `PatchChanged`, no busy state. A read
  that fails keeps the diff on screen and is logged.
- `HistoryPageViewModel.OnWorkingTreeSelectionChanged` refreshes the file already shown, and shows any
  other file as before. A file that was staged or unstaged elsewhere is in the other half, so it is
  another target and is shown fresh. A file that left the lists clears the diff, as it already did.
- `ReloadAsync`, the reader's own re-read, now goes through the same `ReadAsync` and behaves exactly
  as before.

**Created**

- `tests/Enigma.GitClient.Desktop.UnitTests/DiffRefreshTests.cs`, with 11 tests:
  - **The viewer:**
    - an identical refresh keeps the rows, selection and context, and raises no redraw;
    - a changed patch redraws once and clears the selection;
    - a patch that turned into a message says so, and only once;
    - a failed refresh keeps the diff;
    - the reader's own reload still reports a failure;
    - `IsShowing` matches by value;
    - a refresh with nothing shown reads nothing;
    - a newly shown file starts from the default context.
  - **The history, on a real repository:**
    - an unchanged file keeps the rows and the selection;
    - an edited file redraws;
    - a file staged in a terminal is shown as the staged half's diff.

  These wait on a counted read of the real diff service, not on a fixed delay.

## Decisions taken at build time

| Question | Chosen | Why |
|---|---|---|
| How "the same patch" is decided | Patch text plus the flags it does not carry | `FilePatch` has no value equality, and `DiffRowBuilder.PatchText` already renders paths, headers and lines. Word-level highlights are derived from the lines |
| Busy state while a refresh reads | None. The latest read, a refresh included, clears it | A busy flicker every 15 s is noise. A refresh that overtakes the reader's own read must still clear the busy state that read set |
| Who decides "same file" | The history asks the viewer | The viewer knows what it shows. The panel's documented `SelectionChanged` contract is unchanged |
| How the history tests wait | A counting decorator around the real `DiffService`, registered through `TestServices.Build(configure:)` | An "unchanged" assertion after a fixed delay could pass before the refresh even ran |
