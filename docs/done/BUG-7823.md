# BUG-7823 — A drag to the diff's end hangs the app

**Branch:** `bugfix/bug-7823-drag-end-hang`, then `bugfix/bug-7823-arrange-clamp`
**Run:** bugfix/2026-10-05-diff-drag-hang

> Reopened the same day: the first fix kept the offset inside the scroll viewer's limit only, and the
> application still froze in a real window. The stack of the frozen process showed the second limit,
> the view's own arrange pass. See *Reopened — the arrange pass* below; it is what fixed the bug,
> confirmed in the application.

## Summary

Dragging a selection in a diff past its last line — the pointer at the bottom-right — no longer
freezes the application. The selection runs to the end of the document and the editor settles.

- **The cause.** It sits between AvaloniaEdit 12 and the diff editor's settings.
  - While a selection is dragged, AvaloniaEdit's `SelectionMouseHandler` extends it again on every
    `TextView.ScrollOffsetChanged`, then calls `Caret.BringCaretToView(5)`.
  - `TextView.MakeVisible` sets the offset that shows the caret plus a 5-pixel margin, clamped at
    zero but not at the far end.
  - At the end of a diff that offset is out of reach. Nothing scrolls below the last line
    (`AllowScrollBelowDocument = false`), and sideways the text is only 3 pixels wider than its
    widest line.
  - The text view then held an offset its scroll viewer does not allow: 5 pixels past it at the
    bottom. Each time the viewer coerced it back, the drag handler extended the selection, the caret
    asked for the same unreachable offset, and the two fought again.
  - A window re-coerces on every layout, so the fight never stopped. The UI thread never went idle
    (the stuck I-beam, the dead close button), and every round rebuilt the visual lines (the
    memory).
- **The first fix** (`bugfix/bug-7823-drag-end-hang`). The diff editor runs on `DiffTextArea` →
  `DiffTextView`, whose `MakeVisible` moved the requested rectangle inside the extent before the base
  showed it. That kept the offset inside the scroll viewer's limit, but not inside the arrange pass's,
  so it was not enough (see below).

## Reopened — the arrange pass

**Branch:** `bugfix/bug-7823-arrange-clamp`

### What the frozen process showed

The application was run from the first fix and frozen by the drag. 24 samples of its UI thread
(`dotnet-stack report`) were all inside one layout pass:
`MediaContext.Render` → `LayoutManager.ExecuteLayoutPass` → `TextView.MeasureOverride` /
`ArrangeOverride`, rebuilding and shaping visual lines. One sample caught the cycle:
`TextView.ArrangeOverride` → (the scroll offset changed) → `SelectionMouseHandler.ExtendSelectionToMouse`
→ `DiffTextView.MakeVisible` → `TextView.MakeVisible`.

AvaloniaEdit limits a view's scroll offset in two places that disagree:

- its scroll viewer clamps it to the viewport the view was **measured** with;
- `TextView.ArrangeOverride` clamps it again to the size the view was **arranged** at.

In a window the two sizes differ by a rounding; headless they never do, which is why every headless
test passed. The arrange pass took the offset back, the drag handler extended the selection, the
caret was brought into view past that limit, and the next pass took it back again: one layout pass per
frame for as long as the button was held.

### The fix

`DiffTextView.MakeVisible` works the offset out itself.

- `OffsetToShow` applies the base view's rule (bring the rectangle's start or end to the view's,
  its middle when it is too long to fit) and clamps the result to the nearer of the two limits:
  extent minus the larger of the measured and arranged sizes.
- If that is within a pixel (`Tolerance`) of where the view already is, nothing happens. A scroll
  viewer rounds an offset to a whole device pixel, and taking the half pixel for a move would restart
  the fight.
- Otherwise it sets the offset and raises the scroll invalidation, as the base does.
- The arranged size is kept in `ArrangeOverride`, before the base runs, because the drag handler
  brings the caret into view from inside that call.
- `Reachable` is gone.
