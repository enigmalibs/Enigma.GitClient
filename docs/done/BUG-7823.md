# BUG-7823 — A drag to the diff's end hangs the app

**Branch:** `bugfix/bug-7823-drag-end-hang`
**Run:** bugfix/2026-10-05-diff-drag-hang

## Summary

Dragging a selection in a diff past its last line — the pointer at the bottom-right — no longer
freezes the application. The selection runs to the end of the document and the editor settles.

- **The cause.** It sits between AvaloniaEdit 12 and the diff editor's settings.
  - While a selection is dragged, AvaloniaEdit's `SelectionMouseHandler` extends it again on every
    `TextView.ScrollOffsetChanged`, then calls `Caret.BringCaretToView(5)`.
  - `TextView.MakeVisible` sets the offset that shows the caret plus a 5-pixel margin, clamped at
    zero but not at the far end.
  - At the end of a diff that offset is out of reach. Nothing scrolls below the last line
    (`AllowScrollBelowDocument = false`), and sideways the text is only 3 pixels wider than its
    widest line.
  - The text view then held an offset its scroll viewer does not allow: 5 pixels past it at the
    bottom. Each time the viewer coerced it back, the drag handler extended the selection, the caret
    asked for the same unreachable offset, and the two fought again.
  - A window re-coerces on every layout, so the fight never stopped. The UI thread never went idle
    (the stuck I-beam, the dead close button), and every round rebuilt the visual lines (the
    memory).
- **The fix.** The diff editor now runs on `DiffTextArea` → `DiffTextView`. Its `MakeVisible` first
  moves the requested rectangle inside what can be scrolled to (`DiffTextView.Reachable`): the
  extent, or the viewport when the content is smaller. The view only asks for offsets its viewer can
  hold, so there is nothing to fight over. The caret still ends up on screen; only the part of the
  margin past the end of the text is given up.

## Decisions taken at build time

| Question | Chosen | Why |
|---|---|---|
| How to reproduce a hang the headless platform does not show | Hold the drag at the corner and resize the window a pixel at a time, which makes the scroll viewer coerce as a window's every layout does | Headless lays out only on a forced frame, so the fight never kept going on its own. The probe showed 330 scroll events for six resizes before the fix |
| Is the test a real regression test? | Checked by putting AvaloniaEdit's own `TextArea` back: the three short-line drag cases fail ("the text view is at …1096.25, its scroll viewer at …1091.25") and pass with the fix | A fix test that passes on the broken code proves nothing |
| The rectangle larger than what can be scrolled | Cut to it, from the start | It cannot all be shown either way; the start is where the caret's rectangle begins |
| Before the first measure | `MakeVisible` unchanged | There is no extent yet to keep inside |
| Styling of the new view and area | `StyleKeyOverride` to `TextView` / `TextArea` | They keep AvaloniaEdit's templates and styles |

## Deviations & follow-ups

- No deviation from the plan.
- Follow-up: the clamp belongs in AvaloniaEdit's `TextView.MakeVisible` itself. An editor that
  forbids scrolling below the document can be driven into the same fight by any drag. Worth
  reporting upstream, along with the inert `TextEditor.ScrollToVerticalOffset` /
  `ScrollToHorizontalOffset` found in FEATURE-BB60.
- The long-line cases of the regression test already passed before the fix. They keep sideways
  scrolling at the end covered.
- Line endings: no CRLF churn.
