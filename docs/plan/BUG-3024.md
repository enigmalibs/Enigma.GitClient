# BUG-3024 — Unreadable tokens cannot be reset

**Status:** IN PROGRESS
**Type:** BUG
**Branch:** one per phase, see below
**Run:** bugfix/2026-10-23-crash-net-token-reset

## Objective

On 2026-10-23 the user's Windows password was reset at 08:55:57 and DPAPI created new master keys in
that second. `%APPDATA%\Enigma.GitClient\tokens.key`, written on 2026-10-09, is sealed with a master key
this account can no longer decrypt (Crypto-DPAPI 8198, "Master key access failed"): the tokens cannot
be recovered. That is an event outside the application, which it must survive:

1. When the stored tokens cannot be read, the user is always offered a reset.
2. When git falls back to its own sign-in because a token could not be read, the user is told why.

## Context & constraints

- **One exception, three causes.** `FileTokenStore` throws `TokenProtectionException` (sealed) for a data
  key that cannot be unwrapped (`ReadOrCreateDataKey`, "…belong to a different machine or user
  account…"), for one entry that fails authentication (`Unprotect`), and for a tokens file that is not
  JSON (`Read`). Nothing tells them apart.
- **No way out.** The message says "Remove them and sign in again"; nothing in the application does it.
  Disconnect deletes one entry and leaves `tokens.key`, so every later `SetAsync` fails the same way
  until the files are deleted by hand.
- **The crash path.** `ProfilesPageViewModel.ConnectAsync` → `HostAccountService.AddAsync` →
  `FileTokenStore.SetAsync` → `Protect` → `ReadOrCreateDataKey` threw; `ConnectAsync` catches host,
  network and cancellation exceptions only. (BUG-9DE3 adds the safety net; this item adds the
  targeted handling, so the net never sees this one.)
- **Same unguarded read.** `HostRepositoriesDialogViewModel.LoadAsync` reads the token without catching
  `TokenProtectionException`. It runs while the browse dialog is open on the shared host, so a question
  asked from there would replace the dialog: the reset is offered after it closes.
- **Silent fallback.** `GitCredentialResolver` catches `TokenProtectionException` and returns
  `GitCredentials.None` with a log warning (`:137-144`, `:183-190`); one unreadable token drops every
  integration's login, and the user sees Git Credential Manager's prompt with no explanation. The token
  is read in `BuildAsync`, once per sign-in.
- **Principles kept.** Never reset automatically or silently. An unreadable token is an error, never "no
  token" (`TokenStore.cs:267`, FEATURE-22C0 decision in `docs/done/FEATURE-22C0-PHASE01.md`). Nothing on
  the host is touched. Out of scope: recovering the old key, changing the encryption scheme or leaving
  DPAPI, detecting a password reset.
- **Core has no `InternalsVisibleTo`**: a test seam is public API.
- **Tests.** The Desktop tests build the real container (`TestServices`) over a throwaway configuration
  directory, with a scripted `IContentDialogService` and `FakeHostProvider`. On Linux the data key file
  holds the raw key, so a key of the wrong size is how a test makes the real store's key unavailable.

### Shared definitions

- `TokenProtectionReason` (Core/Security): `Unspecified` (the exception's legacy constructors),
  `KeyUnavailable` (the data key is missing while entries exist, cannot be unwrapped, or has the wrong
  size — the whole store is unreadable for this account), `EntryUnreadable` (one entry is damaged, was
  edited, or was sealed under another key), `FileUnreadable` (the tokens file is not readable).
- `TokenProtectionException.Reason`, `.Key` (the entry's key for `EntryUnreadable`, else `null`),
  `.IsStoreWide` (`Reason != EntryUnreadable`). The three existing constructors stay (Reason
  `Unspecified`) and every existing message text stays.
- `ITokenRecovery` (Desktop/Services): the one place the reset is described, confirmed and run.

## PHASE01 — Failure reasons and reset in Core

**Status:** DONE — see `docs/done/BUG-3024-PHASE01.md`
**Branch:** `bugfix/bug-3024-phase01-core-reasons-reset`

### Steps

1. `TokenProtectionReason` and the new members/constructor of `TokenProtectionException`
   (`(TokenProtectionReason reason, string message, Exception? innerException = null, string? key =
   null)`).
2. `IDataKeyProtector` (`Protect(byte[])`, `Unprotect(byte[])`, `Unprotect` throwing
   `CryptographicException` when it cannot) and `PlatformDataKeyProtector` (DPAPI `CurrentUser` on
   Windows, the bytes unchanged elsewhere). `FileTokenStore(IAppPaths, IDataKeyProtector)` — the one
   constructor; registered as a singleton in `AddGitClientCore`; the existing tests pass a
   `PlatformDataKeyProtector`.
3. `FileTokenStore`:
   - reading paths (`TryGetAsync`, `CheckAsync`) read the key without creating one: missing while
     entries exist → `KeyUnavailable`;
   - `SetAsync` creates the key only when the file has no entries; a missing key with entries present →
     `KeyUnavailable` (a fresh key would make the old entries unreadable for good, silently);
   - unwrap failure, or an unwrapped key that is not 32 bytes → `KeyUnavailable` (existing message);
   - entry authentication / format failure → `EntryUnreadable` with the key (existing message);
   - JSON failure → `FileUnreadable` (existing message).
4. `ITokenStore.ResetAsync(CancellationToken)`: under the gate, delete `tokens.key` and `tokens.json`
   (each if present). The next `SetAsync` creates a fresh key, `0600` on Linux as before.
5. `ITokenStore.CheckAsync(CancellationToken)` → `TokenStoreStatus` (`Failure` reason or `null`, `Keys`,
   `UnreadableKeys`): reads the file and the key and authenticates every entry, zeroing every plaintext;
   it never throws a `TokenProtectionException` — it reports it.
6. Tests (`TokenStoreTests`, with a throwing fake protector where DPAPI would be needed):
   - each reason: unwrap failure → `KeyUnavailable`; wrong-size key → `KeyUnavailable`; key file deleted
     with entries left → `KeyUnavailable` on read and on write; tampered / moved entry →
     `EntryUnreadable` with its key; not JSON → `FileUnreadable`; legacy constructors → `Unspecified`;
   - reset deletes both files, a later `SetAsync` / `TryGetAsync` round trip works, the new key file is
     `0600` (skipped on Windows); reset on an empty directory is a no-op;
   - `CheckAsync` on a healthy store, an empty store, each store-wide failure, and one damaged entry
     among good ones;
   - `HostAccountServiceTests`: a connect (`AddAsync`) after a reset of an unreadable store works.

### Acceptance criteria

- Every `TokenProtectionException` the store throws carries one of the three reasons; the existing
  messages are unchanged.
- `ResetAsync` and `CheckAsync` exist on `ITokenStore`, behave as above, and are tested on Linux through
  the protector seam.
- Zero warnings; the whole suite is green.

## PHASE02 — Reset on connect, no duplicates

**Status:** DONE — see `docs/done/BUG-3024-PHASE02.md`
**Branch:** `bugfix/bug-3024-phase02-connect-reset`

### Steps

1. `ITokenRecovery` / `TokenRecovery` (singleton: `ITokenStore`, `IContentDialogService`,
   `IInfoBarService`, `ILogger`):
   - `Describe(TokenProtectionException)` → the sentence the user reads, offering the fix: store-wide →
     "The stored tokens can no longer be read on this computer or by this account (a Windows password
     reset does this). Reset the stored tokens, then give each integration its token again."; one entry →
     "The stored token of this integration cannot be read. Replace its token, or disconnect it.";
   - `ConfirmAndResetAsync()` → `ConfirmDestructiveAsync("Reset stored tokens", …, "Reset stored
     tokens")`; the question says every stored token is deleted, each connected account needs its token
     again, and nothing on the host is touched. On yes: `ResetAsync`, report "Stored tokens reset", raise
     `TokensReset`, return `true`. An I/O failure is reported, `false`;
   - `CheckAsync()` → the store's status (for PHASE03).
2. `HostAccount.IsSameIdentityAs(HostAccount)` (Core): same `Kind`, same base URI (scheme, host, port and
   path, case-insensitive, trailing `/` ignored), same `UserName` (ordinal, case-insensitive), same
   `ProfileId`. Core tests.
3. `ProfilesPageViewModel.ConnectAsync`, after the host validated the token:
   - an existing account with the same identity → `UpdateAsync(existing, token)` (keeping its id; its
     display name changes only when one was typed) and "Token replaced" instead of a second row;
     otherwise `AddAsync` as today;
   - a store-wide `TokenProtectionException` → `ConfirmAndResetAsync()`; confirmed → store the token
     the user typed (no new validation, no second dialog); declined → report the error with `Describe`;
   - an `EntryUnreadable` (not expected on a write) → reported with `Describe`. Nothing reaches the net.
4. The safety net (BUG-9DE3): when the batch's first exception is, or wraps, a store-wide
   `TokenProtectionException`, the dialog also offers *Reset stored tokens* (primary button) and runs
   `ConfirmAndResetAsync()` after it closes.
5. Tests (Desktop, `TokenResetTests.cs` + `ProfileIntegrationsTests`):
   - connect with an unavailable key → the reset question (red, its text names all three facts) → yes →
     the account is connected, its token is the one typed, the key file is new, nothing else asked;
   - the same, answered no → nothing stored, the error offers the reset, no exception escapes;
   - connecting again with the same identity → one row, the new token, same id; another profile or
     another user → a second row;
   - the safety-net dialog offers the reset for a store-wide `TokenProtectionException` and not for
     another exception.

### Acceptance criteria

- Connecting while the key is unavailable never throws; it offers the reset and, once confirmed, stores
  the token just typed.
- Connecting again never leaves a dead duplicate.
- The reset is never run without the confirmation.
- Zero warnings; the whole suite is green.

## PHASE03 — Profiles band, browse and replace

**Status:** DONE — see `docs/done/BUG-3024-PHASE03.md`
**Branch:** `bugfix/bug-3024-phase03-profiles-browse`

### Steps

1. `ProfilesPageViewModel.LoadIntegrationsAsync` also reads `ITokenRecovery.CheckAsync()`:
   - store-wide failure → `IsTokenStoreUnreadable`, `TokenStoreProblem` (the `Describe` text),
     `ResetStoredTokensCommand` (→ `ConfirmAndResetAsync()`, then reload);
   - each row's `TokenState` (`Stored`, `Missing`, `Unreadable`), `HasTokenProblem`, `TokenProblem`
     ("No token stored" / "The stored token cannot be read") and `ReplaceTokenCommand`.
2. *Replace token*: the connect dialog, pre-filled with the row's provider, instance and display name;
   after validation, `UpdateAsync` on that account (its id kept, the user name the host returned). A
   store-wide failure here goes through the same reset offer as connect.
3. `ProfilesPageView.axaml`: a warning band at the top of the page (the repository window's operation
   banner pattern: warning brushes, icon, text, *Reset stored tokens* button) while the store is
   unreadable; on each integration row, the problem text in the warning colour and a *Replace token*
   button while there is one. `AutomationProperties.Name` on the buttons.
4. Browse: `HostRepositoriesDialogViewModel.LoadAsync` catches `TokenProtectionException`, says why in the
   dialog and on the bar (`Describe`), and exposes `TokenFailure`. `HostRepositoryBrowser`: a store-wide
   failure closes the dialog, then offers the reset (`ConfirmAndResetAsync()`); an entry failure leaves
   the dialog saying what to do on the row. The Profiles page reloads its rows after a browse that
   failed this way.
5. Tests: the band and the reset from it; a row with an unreadable entry and one with no token after a
   reset; replace token keeps the id and stores the new token; browse with an unavailable key → the
   dialog closes and the reset is offered; browse with one damaged entry → the summary says so, no
   reset offered, no exception.

### Acceptance criteria

- The Profiles page shows the band whenever the store is unreadable, and the reset works from it.
- Each integration with no readable token says so and offers *Replace token* (and *Disconnect*).
- Browsing never throws on an unreadable token; it offers the reset or points at the row.
- Zero warnings; the whole suite is green.

## PHASE04 — Visible git sign-in fallback

**Status:** TODO
**Branch:** `bugfix/bug-3024-phase04-git-fallback-notice`

### Steps

1. Core, `GitCredentialResolver`:
   - `BuildAsync` reads each sign-in's token on its own: a `TokenProtectionException` is logged (Warning),
     raises `IGitCredentialResolver.TokenUnreadable` (`TokenUnreadableEventArgs`: account, origin,
     reason) and the other sign-ins keep their logins. It still fails open.
   - The outer catches stay for everything else.
2. Core, `ITokenStore.Changed` (`TokenStoreChangedEventArgs`: the key written or deleted, `null` for a
   reset), raised by `FileTokenStore` after `SetAsync`, `DeleteAsync` and `ResetAsync`, outside the gate.
3. Desktop, `GitSignInNoticeViewModel` (singleton: `IGitCredentialResolver`, `ITokenStore`,
   `ITokenRecovery`, `IShellNavigation`): marshals the events to the UI thread; shows "The stored token
   for <host> could not be read, so git is using its own sign-in." once per account per session —
   dismissing it keeps it hidden; a reset, or the account's token written again, hides it; actions *Reset
   stored tokens* (store-wide reason), *Open Profiles*, dismiss.
4. `MainWindowViewModel.SignInNotice`; `MainWindow.axaml`: a warning band under the operation banner,
   same pattern.
5. Tests: Core — one unreadable integration among two raises the event once and the other still signs
   in; the event carries the reason; nothing escapes. Desktop — the notice appears once for repeated
   failures (auto-refresh), stays hidden after dismiss, hides on reset and when the token is written
   again, and offers the reset only for a store-wide reason.

### Acceptance criteria

- A fetch, pull or push whose integration token cannot be read still runs (git's own sign-in), and the
  repository window says why, once.
- The notice offers the reset or the Profiles page, and goes away when the problem is resolved.
- Zero warnings; the whole suite is green.

### Manual check (Windows), recorded in the completion doc

1. Back up `%APPDATA%\Enigma.GitClient`, close the app, overwrite `tokens.key` with random bytes.
2. Connect: the reset is offered, and the connect then works.
3. Fetch: the notice is shown.
4. Force an exception from a command: the dialog appears and the app keeps running.

## Out of scope

- Recovering the old key; changing the encryption scheme or leaving DPAPI; detecting Windows password
  resets.
- Telling a wrong-but-well-sized key from damaged entries on Linux (the file format has no key check
  value; adding one changes the scheme).
