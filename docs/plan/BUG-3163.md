# BUG-3163 — Racing write test hangs on Windows

**Status:** TODO
**Type:** BUG
**Branch:** `bugfix/bug-3163-racing-test-hang`
**Run:** vibe/2026-10-08-slow-hanging-tests

## Objective

`AtomicFileTests.AReaderRacingTheWriter_AlwaysReadsAWholeDocument` finishes, green, on Windows, and can
never hang again. The product bug it exposes is fixed: an atomic write lands even while another
reader has the file open.

## Context & constraints

- **The hang, reproduced on 2026-10-08:** the test ran for more than 3 minutes at 100% CPU, where it
  should take under a second. MTP's `--timeout 45s` did not stop it.
  - On Windows, `File.Move(temporary, path, overwrite: true)` is refused while another handle has the
    target open without `FileShare.Delete`, which is how `File.ReadAllText` opens it. The error is an
    `UnauthorizedAccessException` (access denied).
  - The test's writer dies on its first refusal. It never cancels `stop`, so the reader loop
    `while (!stop.IsCancellationRequested)` spins forever, and `Dispose` never removes the temporary
    directory. There are 16 `enigma-atomic-*` leftovers in `%TEMP%`.
- **A product bug too.** `AtomicFile` writes:
  - `settings.json` (`SettingsService`);
  - the identity profiles (`IdentityProfileStore`);
  - the recent repositories (`RepositoryListStore`);
  - the hidden branches (`HiddenBranchStore`).

  With several instances side by side, one instance reading a file while another writes it makes the
  write throw. The callers catch it and log a warning, so the write is silently lost. This happens on
  Windows only: on Linux, a rename over an open file succeeds.
- Same diagnosis as the abandoned BUG-6EAA, whose work branch is gone. That item measured the retry
  budget: against a reader re-opening the file in a tight loop, 1500 writes with up to 50 attempts
  10 ms apart all landed, and the worst took 16 attempts. A real reader holds the file for
  microseconds.
- `AtomicFile` is a static class with no logger and no clock; its sync callers run on the UI thread.

## Steps

1. `src/Enigma.GitClient.Core/Configuration/AtomicFile.cs`, Windows only: while the target is held
   open, retry the final replace.
   - Up to 50 attempts, 10 ms apart.
   - Retried refusals: access denied (`UnauthorizedAccessException`), and a sharing or lock violation
     (`IOException` with `HResult` `0x80070020` / `0x80070021`).
   - Any other error, and the last refusal, surface as before. The temporary file is still deleted.
   - `WriteAllText` waits with `Thread.Sleep`. `WriteAllTextAsync` waits with `Task.Delay` under its
     cancellation token, so a cancelled wait stops retrying.
2. `tests/Enigma.GitClient.Core.UnitTests/Configuration/AtomicFileTests.cs`:
   - the racing writer cancels `stop` in a `finally`, so a writer that fails fails the test instead of
     hanging it. The assertions are unchanged.
   - new: a write made while a reader holds the file lands once the reader lets go, sync and async.
   - new, Windows only: a reader that never lets go fails the write with the refusal, and no temporary
     file is left behind.

## Acceptance criteria

- The racing test passes on Windows in seconds, and cannot hang: a writer failure is a test failure.
- A write made while a reader holds the file lands once the reader lets go.
- A reader that never lets go still fails the write on Windows, after the bounded retry, with no
  temporary file left.
- Linux behaviour is unchanged (the retry is behind `OperatingSystem.IsWindows()`).
- Build: zero warnings. Core unit and integration suites green, the racing test included. The Desktop
  suite is compiled, not run (standing instruction).

## Out of scope

- How readers open the files (`FileShare.Delete`): another process's reader is out of reach anyway.
- The Desktop test teardown on read-only git objects (the other half of BUG-6EAA): the Desktop suite
  must not run on this machine, so a fix could not be verified.
- Cleaning up the old `enigma-atomic-*` leftovers in `%TEMP%`.
